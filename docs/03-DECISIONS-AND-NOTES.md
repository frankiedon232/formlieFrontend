# 03, Decisions, Interpretations and Items to Confirm

Edit this file whenever a decision changes.

## Interpretations made from the brief

1. **"CEO on shared links"** is read as **SEO** (meta title, description, Open Graph image, canonical, noindex toggle).
2. **"Role level security"** in the backend brief is read as **PostgreSQL Row-Level Security (RLS)**. Role-based access (RBAC) is a separate, later feature.
3. **Tenant vs organisation:** tenant = subscribing account + subdomain; organisation = unit inside the tenant. Both IDs on every tenant table.
4. **Re-editing a published form:** creates a new draft version; the published version **stays live** until the draft is published. Option to "unpublish while editing" if the owner wants the form offline.
5. **"Same token should not be sent twice":** every issued token is unique (Fernet random IV + timestamp); refresh tokens are single-use and rotated; per-request replay is blocked by the envelope nonce. The access token itself is reused across requests until its 15-min expiry, making every access token single-use would force a round trip per request.
6. **"Microservice architecture":** modular monolith API + independent Celery worker services over RabbitMQ events, designed so modules can be split out later.
7. **"No reinventing CSS":** use Nuxt UI components, their `ui`/`class` props and Tailwind utilities only. The one exception is user-designed form themes, applied through CSS variables on the rendered form.
8. **Drag and drop:** Nuxt UI has no DnD primitive, so we use `vue-draggable-plus` (SortableJS), the only extra UI dependency, with keyboard alternatives.
9. **Live collaboration:** planned as an optional later phase (Yjs CRDT over WebSockets) once the single-user builder is stable.

10. **Product name:** "Formalie" everywhere (some early docs said "Formly").
11. **Backend dev port:** `https://formalie.dev:5004` (configurable via `NUXT_API_PROXY_TARGET`).
12. **Mock API speaks the real protocol:** the Nitro mock performs the ECDH handshake and checks/produces real envelopes (expiry, nonce replay, AAD, method/path binding, CSRF). Envelope code lives in `shared/utils/crypto/` and is shared by browser and mock, so switching to FastAPI only needs both sides to match SECURITY-PROTOCOL.md.
13. **Mock vs proxy:** `NUXT_PUBLIC_API_MOCK=true` mounts `server/mock` at `/api/**`; otherwise `server/proxy/api.ts` forwards `/api/**` to the backend with `X-Forwarded-Host`. Read at startup, restart dev after changing it.
14. **SSR public forms and the envelope:** for server-rendered public form pages (`/{formKey}/fill` · `/embed`), Nitro performs its own handshake with the API (acting as a client, same protocol, scoped to the tenant host) to fetch the published schema; the browser then does its own handshake for submit. Finalised in F10.
15. **Draggable modals:** Nuxt UI modals have no drag; we use `@vueuse/core` `useDraggable` on the modal header plus arrow-key moves (F1). On phones modals stay docked.
16. **Languages:** `@nuxtjs/i18n` with 20 languages (see FRONTEND-SPEC §10). Strategy `no_prefix`; cookie `formalie_locale`. Yoruba, Hausa, Igbo, Amharic etc. can be added by one entry in `shared/utils/i18n/locales.ts` + one JSON file.
17. **TypeScript 6.0** pinned: typescript-eslint does not support TS 7 yet.
18. **`custom.css` removed:** `main.css` holds only the Tailwind/Nuxt UI imports and `@theme` tokens (CLAUDE.md rule 1).

19. **Host classification** is one pure, shared, unit-tested function (`resolveHostContext`): manage/root/www → manage entry; `{sub}.{rootDomain}` and `{sub}.localhost` → tenant; localhost/IP → manage, or a tenant via a **dev-only** `?tenant=` override (for phones on the LAN, which have no hosts file); reserved/nested/malformed → "workspace not found"; any other domain → custom domain (resolved by the API, later). The subdomain is never trusted alone (token must match, FRM-TEN-1003).

20. **Modal drag offset uses margins**, not `translate`/`transform`: Tailwind 4 centres Nuxt UI modals with the `translate` property and animates them with `transform`; margins move the dialog without fighting either.
21. **Nuxt UI 4.11 missing locale strings:** `dashboardSearch.title/description` and `dashboardSidebar.description` are absent from Nuxt UI's messages, so we pass our own translated `title`/`description` props. Re-check when upgrading Nuxt UI.
22. **User menu lives at the bottom of the sidebar** (as in the design reference); the navbar keeps search, notifications, language and theme.

23. **Design images are the exact target** (owner, 2026-10-02), supersedes "don't copy colours": monochrome primary (`--ui-primary` = neutral-900 light / neutral-100 dark in `main.css`), rail + menu sidebar, search left in the top bar.
24. **Theme toggle placement** follows the design (sidebar SYSTEM → Dark mode); navbar theme button only below `lg` where the sidebar is hidden.
25. **Breadcrumbs** live in the top bar right after the search field (owner, 2026-10-02: avoid extra vertical space).
26. **Nuxt Icon endpoint moved to `/_nuxt_icon`** and icons are client-bundled: `/api/**` belongs to the backend (mock, dev proxy, Nginx in production).

27. **Font: Manrope** (Google, via `@nuxt/fonts`), weights 300–700; titles 600, body 400/500. Identified by comparing the design's glyphs (straight-tailed y, descending J, single-storey g, flagged 1, round geometric o) against candidates; Onest was the runner-up. Swap = one line in `main.css`.
28. **Language flags** come from the `circle-flags` icon set (`@iconify-json/circle-flags`), one flag per language variant (en → US, pt → BR, ar → SA, sw → KE …), shown on every language switcher.

29. **API client is framework-free** (`app/utils/api/client.ts`, transport injected) so the protocol is unit-tested against a fake server; `useApi()` only adds Nuxt bits. Session key, CSRF token and access token live in closures / module refs (memory only).
30. **Recovery policy** (once each per request): FRM-SEC-1004 → re-handshake, FRM-SEC-1006 → new CSRF, FRM-SEC-1002 → resend, FRM-AUTH-1001 → refresh; FRM-AUTH-1010/1011/1012 or failed refresh → session cleared (F3 redirects to login).
31. **Confirm dialogs** use one `<AppConfirmDialog>` in the layout driven by `useConfirm()` state, no component imports (CLAUDE.md rule 2).
32. **DataView: the URL is the source of truth**; table/grid preference is the only thing in localStorage (`formalie:view:<id>`, non-sensitive).
33. **`secondary` colour = violet** (closed status, as the design's purple badges); status → colour: draft warning/amber, published success/green, closed secondary/violet, archived neutral.
34. **`@internationalized/date`** added as a direct dependency: Nuxt UI's `UCalendar` needs its date objects and pnpm's strict layout requires the direct install.

35. **Header bar is the page header** (owner, 2026-10-02): title, subtitle, breadcrumbs and page buttons live in the top bar; `AppPageHeader` removed. The global "New form" button left the top bar (the rail's **+** and the Forms page actions cover it).
36. **Footer** added (`AppFooter`): © · version (`runtimeConfig.public.appVersion` from package.json) · Help · Shortcuts. Privacy/Terms links once the website URLs are known.

37. **Cross-subdomain signup hand-off:** tokens live in memory and the refresh cookie is host-scoped, so signup returns a one-time `ticket` URL on the new subdomain (`/auth/welcome?ticket=`), exchanged there for a session.
38. **Codes everywhere instead of links:** find-workspace and password reset use the same 6-digit OTP UI as login; no enumeration (same answer for unknown emails).
39. **Pending challenge in memory only:** reloading the code screen starts over (no challenge ids in storage).
40. **Middleware order:** `01.tenant.global` (host → workspace, manage-only pages) then `02.auth.global` (restore via refresh cookie, then guard). Page meta: `auth: 'guest' | false`, `manage: true | 'only'`.
41. **Last workspace** is remembered in a non-sensitive cookie on the root domain (`formalie_ws`, name + subdomain) so manage.* can offer "Continue to …".
42. **Brand icons** for sign-in providers come from `@iconify-json/simple-icons`.
43. **Installing packages while dev runs** breaks the running server (`postinstall` regenerates `.nuxt`): restart `pnpm dev` after `pnpm add`.

44. **Global positioning everywhere** (owner, 2026-10-02): the sign-in showcase tells the platform story, any form, your data, your database, access control, privacy & compliance controls, 20 languages, any region. Mock data uses international names (no country-specific people, cities or phone numbers).

45. **Customer databases, launch set:** MySQL, MariaDB, Oracle, PostgreSQL, SQL Server (single list: `shared/utils/integrations/databases.ts`, with default ports for F12, Data sources), or Formalie's own encrypted storage. Copy says "{count}+ databases" from that list so it never implies a single engine.

46. **Social signup** (owner, 2026-10-02): manage.* offers every provider on the first signup; a workspace's sign-in page shows only the methods its admin enabled (Settings → Authentication, F14). New workspaces start with email + password (+ the provider used to sign up, backend).

47. **Audit trail early** (owner, 2026-10-02): the audit trail is its own phase (F4) right after sign-in, not grouped with RBAC at the end. Every later phase records its actions (mock first, backend later) and shows them in `/audit`; only the `audit.read` / `audit.export` permissions wait for Roles & access (F22).

48. **Audit trail details** (F4): one event catalogue (`shared/utils/audit/events.ts`) feeds the mock, filters, labels and exports. Users carry a simple `role` (owner / admin / member) until Roles & access (F22); members get FRM-PERM-1001 and the menu entry is hidden. Failed sign-ins by unknown emails are recorded with `actor.id = null`. Exports run as background jobs; the file is fetched from a plain, single-use, 10-minute download link (a browser download cannot carry the envelope). The detail panel is addressable (`/audit?event=<id>`) so an event can be shared. Mock IPs come from the reserved documentation ranges.

49. **Onboarding** (F5): a full-screen wizard (`/onboarding`, own layout) with five optional steps, company, branding, regional settings, team, first form, and a live preview. The server stores progress per workspace so it resumes anywhere; the stepper is non-linear (any step can be opened). Defaults come from the device and country (country from the browser language, timezone from the device, currency / date / number / week start from the country) and are only suggestions. Shown after signup (welcome hand-off) and reachable later from Settings and the user menu (owners / admins). Finishing opens the chosen template or a blank form. Logos go through pre-signed uploads (PNG / JPEG / WebP ≤ 2 MB, magic-byte check, no SVG).

50. **Session lifetime** (owner, 2026-10-02: "leave for at least 1 hour if idle"): 15-min access tokens refresh silently; the session itself ends only after **60 minutes of inactivity** (sliding) or 7 days at most. Early sign-outs during development came from the mock losing its in-memory sessions on every reload of server code; mock sessions and workspaces created by signup now persist in `.data/mock/` (gitignored, passwords hashed), and an unknown access token triggers a refresh instead of a sign-out.

51. **Forms lifecycle** (F6): statuses Draft → Published → Closed, plus Archived (keeps the status it came from, so Unarchive puts it back) and Trash (soft delete, 30 days, then removed; permanent delete and Empty Trash ask first). Every change carries `row_version`; a conflict refreshes the list with a clear message. Actions live in one composable (`useFormActions`): busy row, toast, list + sidebar counts refreshed. A form opens on an overview page (`/forms/{id}`) with its activity until the builder (F7) adds editing. Import accepts FormSchema v1 JSON (validated and previewed first, 1 MB max).

52. **Form builder** (F7): three panes on laptops and up (palette · the real form on a page card · inspector); below that the canvas with a floating “Add field / Field settings” bar opening slide-overs (tablet) or bottom drawers (phone). The canvas shows fields exactly as respondents see them (one renderer for builder, preview, public form and embed), dressed in the reference style, the design images are **look and feel, not features** (owner). Rows on a 12-column grid; dropping next to a field shares the row evenly. Every edit is undoable (snapshots, typing grouped). Autosave ~1 s after the last change with `row_version`; a conflict pauses saving. Field keys follow the label until the form is first published, then stay fixed. Payment is listed as “soon”. Rich text uses Nuxt UI's own editor (UEditor; TipTap comes with Nuxt UI) plus `@tiptap/extension-text-align` (owner-approved) for alignment. Answers are **HTML** because Markdown can't keep alignment; the server sanitises them with a strict allow-list on submit and wherever they are shown, and max length counts the visible text. Full toolbar (paragraph / heading 1–6, code, code block, alignment) is the default; Basic stays available.
53. **Form logic, calculations and versions** (F7): rules are stored in `schema.logic` as `{ id, when: { all | any: [{ field, op, value }] }, then: [{ action, target }] }` with field / page **ids** (keys may change before first publish). One evaluator (`shared/utils/forms/logic.ts`) runs in the preview, the public form and the API. A “show” rule hides its target until it matches; a “hide” rule hides it while it matches; page jumps attach to the page holding the first condition's field, and the first matching jump wins. Calculated fields use a small arithmetic parser (numbers, `{key}`, + − × ÷, brackets), never `eval`. The editor shows each rule as a plain-language sentence built from translated fragments, so word order works per language. Build / Logic / Versions are three routes sharing one frame (`FormsBuilderFrame` + `useBuilderSession`); leaving any of them saves the pending draft first. Versions are compared field-by-id (added / changed / removed). Restore copies a version into the draft (never straight to live). Collapsible sections fold the rows under a section heading; folded required fields still count and unfold on submit. Canvas virtualisation is deferred (it fights drag and drop) until measured need; option sets move to F15.
54. **Builder feedback round** (owner, 2026-10-02): fields on the canvas work so they can be tried out (typed values are never saved); double-click a label or press F2 to rename in place. The inspector calls the caption **Label**, one word that fits questions, headings, hidden and calculated fields. Field keys are read-only (copy button) and get a 4-character suffix from the field id (`full_name_k3x9`): unique, stable while the label changes before first publish, and formulas follow a renamed key. Help text moved into an info popover beside the label. Form controls use a smaller radius than the portal (`--ui-radius: .25rem` on the form), spacing is tighter, and columns follow the **form's own width** (container queries) so the phone preview stacks every field. Label position (top / beside) is one form-wide setting, chosen on New form and in Form settings; "beside" is decided by the form's width (named container `form`), so it also holds in half-width columns, and phone-width forms stack. All labels share one width per form (`--form-label-w`, from the longest label, max 22 characters / 30 % of the field, so the input takes most of the row) and are end-aligned, so labels hug their inputs and every input lines up (owner: uniform, but beside, not far left). Every date input is Nuxt UI (`UInputDate` / `UInputTime` + `UCalendar`), answers stored as ISO text. Fields can be read-only or disabled, never required then (UI blocks it, renderer ignores it, publish check `locked_required`, logic flags "require" on them). Upload types are picked from a grouped, searchable catalogue (`shared/utils/forms/file-types.ts`, any type by default, custom `.ext` allowed) and files show as thumbnails. Logic covers lists, ranges, counts, text starts / ends, and actions for pages, optional, enable / disable, set / clear value and skip to end; the editor is two numbered steps (IF / THEN) with column labels, descriptions per action, starter rules and conflict checks. Formulas gained comparisons, `if()` and functions; choice options can carry numbers. Saved fields and option lists (palette tabs Saved / Lists) are a workspace library, lists are the first part of F15 option sets.
55. **Option lists roadmap** (owner, 2026-10-02, planned for F15, not built yet): five kinds of list, static (today), large with autocomplete, cascading with named levels (e.g. State → City → Location), with details that auto-fill other fields, and dynamic (another form, a database, a JSON URL, a refreshed CSV). Large / tree / dynamic lists keep their items on the server and load per parent or per search; fields point at a list with `option_source` (list, level, parent field) and fill others with `props.fills`. Answers store value + label (+ path) so exports survive list changes. Public lookups are rate limited and only serve lists of the published form. Plan and phasing: [OPTION-LISTS.md](OPTION-LISTS.md). The endpoint family is `/option-lists` (one name, replacing `/option-sets`).
56. **Layout blocks** (owner, 2026-10-02): sections are a real heading block (title size, optional description, divider line, start / centre) with "Section title" / description placeholders on the canvas and double-click editing of both. Paragraphs are written on the canvas with Nuxt UI's editor (bubble toolbar: bold, italic, underline, link, lists, alignment) and stored as HTML; respondents see them through a read-only editor, which keeps only known nodes, no `v-html`. Images upload straight from the canvas (new upload purpose `form_image`, members, 5 MB, PNG / JPG / WebP / GIF / safe SVG, kept across mock reloads) or take an https link; size 10–100 % by dragging the edge handle (← → in 5 % steps on the handle) or presets, alignment, caption, optional link (http/https only) and rounded corners; missing alt text is flagged. Dividers get solid / dashed / dotted and three spacings.
57. **Answer validation** (owner, 2026-10-02): one validator (`shared/utils/forms/validate.ts`) for the renderer and the API, formats (email, web address, phone with country code), number range, text length, pattern (with the builder's own message), choice counts, file count, date-range order and every required address part (street, city, country, postal code unless switched off for countries without one, region when switched on). Messages name the field. After a first failed Next / Submit errors update live as answers are fixed; missing address parts are highlighted individually.
58. **Form themes** (F8): a theme is a set of tokens (`shared/utils/forms/theme.ts`) stored on the form schema (`schema.theme`), so it is saved with the draft, published with a version and restorable. A form without a theme uses the workspace default, brand colour and logo from onboarding, so every shared form looks finished. Tokens are applied as CSS variables on the form page root only (`--ui-*` drive Nuxt UI inputs, buttons and text inside; the portal is untouched); invalid stored tokens fall back group by group, so a broken import never breaks a page. Button text colour is chosen automatically for contrast; the designer warns below 4.5 : 1. Fonts are system / already-loaded stacks for now (no external font requests from public forms); more web fonts need a self-hosting package. Images use the same `form_image` upload as image blocks.
59. **Saved themes and new field types** (F8, owner 2026-10-02): a saved theme is a workspace copy of the tokens (`/themes`); applying one copies its tokens into the form (`schema.theme`) and remembers `theme_id`, so editing the library later never silently changes published forms. Deleting a theme in use is allowed after a warning with the count, forms keep their copy. New field types cover global needs (full name with optional title / middle, consent, duration, percentage, language / time zone / currency from `Intl` so names show in the respondent's language) and IT / finance identifiers (IP address v4/v6, domain, MAC, IBAN with checksum, SWIFT / BIC, colour). All checks live in the shared validator; examples use reserved documentation values (192.0.2.x, 2001:db8::, example.org). More types can be added as the owner lists them.
60. **Data sources & databases phase** (owner, 2026-10-02): connecting customer databases is its own phase, **F12**, after Responses and before Settings (later phases renumbered F14–F22). It covers connections, sending form data (mapping, create table, background delivery with retries, backfill), a database explorer, a query editor and other database operations (row edits, imports, exports). Principles: credentials write-only and encrypted at rest; every query runs on the server with time-outs and row caps; read-only by default, changing statements need a read + write connection and a confirm; every query and data change is audited; fine-grained permissions arrive with Roles & access (F22), admins only until then. The SQL editor needs a code editor package (e.g. CodeMirror 6), to be approved before F12 starts. Dynamic option lists (F15e) read from these connections.
61. **API service addresses, no encrypted ids in the URL** (owner question, 2026-10-03): endpoints are `https://api.formalie.dev/{apiKey}/{endpoint}` (production `api.formalie.com`). The first segment is a short **random public handle** per organisation (10 letters / digits, e.g. `k7Qm2xP9aZ`), not an encrypted tenant / organisation id. Why: (1) an address is not a secret, it travels in app code, logs and proxies, so encrypting it adds no protection; anyone holding the URL could replay the encrypted value anyway; (2) encrypted ids are long (40+ characters with IV and tag), depend on a key that can never change without breaking every integration, and can leak structure; (3) a random handle reveals nothing, is short, and can be rotated (old handle kept for a grace period). Security comes from the request, not the address: bearer token (static, or dynamic short-lived tokens from client id + secret), optional HMAC request signing, allow / block lists, rate limits and TLS. The backend maps handle → tenant + organisation and checks the token belongs to the same organisation, so no tenant / organisation id headers are needed (and none can be spoofed). The portal's own encryption envelope (SECURITY-PROTOCOL §1–3) stays for the portal; third-party callers use standard HTTPS + tokens, which every language supports.
62. **Public form links** (owner, 2026-10-03): `https://forms.formalie.dev/{formKey}/fill` and `/embed` for workspaces without their own subdomain, `https://{sub}.formalie.dev/{formKey}/fill` · `/embed` with one (production `.com`). Replaces `/f/{slug}`. `forms` is a reserved subdomain; links are built in one helper (`shared/utils/urls/public.ts`); short links move to `forms.formalie.com/s/{code}`. The `forms.*` host serves form pages without a workspace session (the form key identifies the workspace), built in F10.
63. **API service is its own area and phase** (owner, 2026-10-02/03): F13, after Data sources (it writes through the same storage / destinations); own rail icon and menu, own analytics and, in F21, its own dashboard (as do Forms and Data sources). Endpoints are built one form at a time (any number), methods limited to GET / POST / PUT / DELETE for now. Later phases renumbered F14–F22.
64. **Field access (audience)** (owner, 2026-10-03): every input field can be for **everyone** (default, overrides all) or only for some **departments**, **roles** or **people** (all of that kind, or a multi-selection). Stored as `field.audience = { mode, all, ids }`. A restricted field is **never required**, people it isn't meant for must still be able to submit, enforced in the inspector, the form, the publish check (`locked_required`) and logic. It is separate from read-only / disabled (how a field can be answered). Public respondents never see restricted fields (F10); answers to restricted fields are shown only to the same audience when reviewing responses (F11), which supports decisions on submitted data. The picker reads `GET /directory` (departments, roles, people), real departments with Users (F17), custom roles with Roles & access (F22).
65. **Payment field** (owner question, 2026-10-03): collects a payment as part of submitting, fixed, chosen or **calculated** amount (formulas) in any currency, through payment providers the workspace connects (global and regional), test and live mode. Card details never touch Formalie (provider-hosted checkout); we store status, reference and amount, confirmed by the provider's webhook. Lands with integrations (F15 → Payments); stays "soon" in the builder until then.
66. **AI assistant** (owner idea, 2026-10-03): its own phase **F19** (after Analytics, so there is data to analyse) and its own rail area; also offered in context (builder, templates, responses). The assistant proposes, a person applies; workspaces control what it may read and can keep personal data out; every request is in its history and the audit trail. Provider / model are backend decisions taken when F19 starts. Later phases renumbered F20–F22.
67. **Templates, how F9 is built** (owner question, 2026-10-03): the framework first (model, authoring kit with schema tests, gallery, template page with preview / statistics / forms made from it, use-template flow, workspace templates), proven with two full categories, then the remaining categories in batches, all inside F9 (5 milestones, each committed). Every template has its own design (theme), realistic fields and, where the domain needs it, calculations (risk score, totals, averages, ratios). Content is authored in English with per-template message files so all 20 languages are added in milestone 5. Templates stay in the Forms area (Resources → Templates), not a rail area of their own.
68. **No duplicate submissions** (owner question, 2026-10-03; built in F10): three layers. (1) The form: Submit is busy and disabled from the first click until the answer comes back. (2) The request: each fill-in session gets a submission id when it starts; Submit sends it as an `Idempotency-Key`. The API stores the first response for that key (kept 24 h, per form) and answers any repeat, double click, a retry after a dropped connection, the back button, with the same response id, never a second response; a session that has submitted is closed. (3) The form's own rule, when switched on: "one response per person", signed-in respondents by account, others by a signed cookie and, when the form asks for an email, by that email; plus rate limits per form and IP and the captcha. Offline / slow networks: the app retries with the same key, so a retry can never double-count.
69. **Navigation follows the domains** (owner, 2026-10-03): Templates and Themes open submenus with the six most recent items plus "All …" (same pattern as Forms); Responses opens status submenus (All, New, Reviewed, Approved, Rejected) and Exports, with counts from `/navigation/counts`; Integrations (webhooks, API keys, app integrations) live in the API service area, F13 is now "API service & integrations", F15 "Option sets & payments".
70. **Folders** (owner, 2026-10-03): folders group forms by team, client or project, they are workspace organisation, not template categories. Managed under Forms → Folders (create, rename, delete) and created on the fly in "Move to folder"; chosen when creating a form. A folder that still holds forms can't be deleted (`FRM-FORM-1013`), move its forms first; forms in Trash simply lose the folder. Folder pages with statistics come with F11.
71. **File limits are enforced where the file is chosen** (owner, 2026-10-03): type (the field's accepted types, drag and drop skips the picker's filter), size (max MB per file) and count (max files) are checked on every pick or drop; anything outside is taken out again and the person is told, a notification plus a message under the field, so nobody wonders why a file "didn't work". The API checks the same limits on upload (F10).
72. **Themes catalogue** (owner, 2026-10-03; built in F9 milestone 2): like templates, themes come in three kinds, system (Formalie's designs), saved (from a form's design) and created (in a theme editor without a form). System themes are read-only; duplicate to change.
73. **Languages go with the form** (owner question, 2026-10-03): every form has a main language (`settings.language`, chosen in Form settings) and may offer more, with translated questions, options, help and messages per language (template content arrives in all 20 languages in F9 milestone 5). A public link opens in the respondent's browser language when the form offers it, otherwise the main language; `?lang=xx` forces a language, so per-language links, embeds and QR codes can be shared. A switcher appears when a form has several languages; the language used is saved with each response. System texts (buttons, errors), dates, numbers and right-to-left layout follow the chosen language. Built with the public pages (F10). *Update 2026-10-04 (owner, decision 99): the browser language no longer decides; a form opens in its main language unless the link says `?lang=`, and respondents switch with the switcher.*
74. **Form link and embed are different addresses on purpose** (owner question, 2026-10-03): `/{formKey}/fill` is the full branded page (sharing, SEO, password / expiry pages, counted as "link"); `/{formKey}/embed` is the form without page chrome for iframes (auto-resize, allowed domains only, counted as "embed"). The Share card will offer the ready iframe code rather than the bare embed address (F10). Both live in this same Nuxt app as server-rendered public routes with their own layout, no dashboard code, no workspace session, on `forms.formalie.com` and workspace subdomains.
75. **QR codes** (owner, 2026-10-03): generated in the browser with `uqr` (owner-approved), drawn as SVG paths (no injected markup). Two styles: **branded**, a card with "Scan to open", the code with the organisation's logo (or initials) in the centre, the organisation and form name below and the Formalie mark in the footer; workspaces without their own subdomain get Formalie branding throughout, and **plain** (the code alone). Colours: the form's, the workspace brand, black, presets or any colour (contrast warning). Error correction "H" keeps the centre badge scannable. 113. **Response storage** (F12 M2, 2026-10-05). Each form keeps its responses either in Formalie's encrypted storage (the default) or in one table on one of the workspace's connections (one storage per form, not several destinations: the database is where the responses live, not a copy). The table is created from the form (named prefix + form name, in the connection's response-table schema; columns from the questions' keys, types per engine; the response id is the primary key) or is an existing table of theirs (Full access; columns matched by name and common aliases; a column for the response id is required, Formalie can add one). Options: a new row per response or update-or-insert on a key; answers with several values as JSON or readable text; choices by value or label; extra facts (response number, respondent's email, review status). Formalie keeps each response in its encrypted queue until the database confirms it; deliveries run in the background with retries (1, 5, 15, 60 minutes, then 6 hours), can be paused (responses are held) and retried by hand; earlier responses are sent for a date range with progress, never twice. Questions added later get a column with one click (ALTER TABLE … ADD); nothing is dropped. Responses are shown the same way wherever they are stored (the backend reads them back from the table). Setup lives on the form (`/forms/[id]/storage`, from the overview card "Where responses are stored"); the overview of every form storing in a database is Data sources → Destinations. Admins only until F22. Standard for tables Formalie creates (owner 2026-10-05, not a choice): one row per response, found by its response id (update-or-insert on the response id: a new response adds its row, an edit or review change updates it, a retried delivery never duplicates); only tables of theirs offer the writing choice. "Create a table from the form" is marked Recommended; a table of theirs is for tables other systems already use, with the caution that later changes to it can stop deliveries. For their own systems, a Formalie table's panel offers a ready `CREATE OR REPLACE VIEW` (SQL Server `CREATE OR ALTER VIEW`) naming each column after its question, which they run themselves.
